Frame rate

Does the voice cost frame time?

The last round's report found this build about 0.7 ms a frame slower than the one before, at the smallest test size, 320 by 180, and named the voice recordings as the likely cause. Those two builds had been timed one after the other, six tours each. Before changing the game, this step tested whether the difference was real.

First try: five builds in a fixed order

Four rounds, always in the same order: last round's build; the same build with the voice text added to its script but never used; this build; this build without the recordings; and this build with the recordings kept as page text. Each run is a fresh browser and the whole tour: five places, 90 frames each.

This build came out +0.30 ms a frame against last round's, with a 95% interval from −0.93 to +1.53: no answer either way. Another number from the same runs is more telling. Last round's build with the unused voice text came out 0.73 ms a frame faster than the same build without it, in all four rounds, with a 95% interval of −1.14 to −0.31 ms that leaves out zero. Text that is never used does no work in a frame, so a confident-looking difference that size comes from the run's second place in each round, or from incidental effects such as where things land in memory. Measurement research describes exactly this: small, innocent changes to a setup can shift timings by several per cent (Mytkowicz and others, 2009), and builds should be compared over repeated runs with confidence intervals (Georges and others, 2007).

Answer at this size: no measurable cost. Read within rounds and with the place in the round taken out, this build is +0.18 ms a frame against last round's (95% interval −0.16 to +0.52), and without the warm-up +0.02 ms (−0.32 to +0.36). Both intervals include zero. The interval does rule out the 0.7 ms reported last round, and any cost above about 0.5 ms; a smaller one cannot be ruled out at this precision. Drawing alone moved by −0.04 and +0.01 ms. The warm-up stays: it costs nothing here, and it lets the first "Fish on!" start without waiting for its sound to be decoded. The larger screen comes next.

The place in the round mattered about as much as anything else: running second moved a run by −0.03 ms against running first, and running third by +0.13 ms. That is the size of effect a fixed order turns into a false difference between builds. Without the place taken out, the plain within-round differences say the same: this build +0.18 ms (−0.25 to +0.61), without the warm-up +0.02 ms (−0.21 to +0.25).

Profiles

Two tours of each of the three builds with the processor profile on. The same functions take the same time in all three, and no voice code is among the 40 busiest. Garbage collection over the whole tour took 147 and 162 ms in last round's build, 149 and 165 ms in this one, and 94 and 91 ms without the warm-up. Last round's build has no recordings at all and collects as much as this one, so the recordings are not adding collection work. Profiling slows every frame by more than the differences sought, so these tours show where the time goes, not which build is faster.

Work or waiting: every thread's processor time

A frame takes longer either because the game does more work or because it waits, for instance for a processor core while other threads use them. To tell the two apart, whole tours of both builds ran again at this size, two of each in turn (last round's, this, this, last round's), while a new tool, tools/cpu-by-thread.py, read the processor time of every thread of the browser from the system every half second. No thread does more work in this build. The page's main thread, which runs every timed frame, used 5.54 s with last round's build and 5.52 s with this one; the software renderer's workers 151.4 and 151.8 s; every other thread within 0.19 s, less than two tours of the same build differ. If the recordings, the buttons or the voice round's new styles made the browser do more while playing, it would show here as extra time on some thread. The same tours also timed their frames: 11.32 ms with last round's build and 11.28 ms with this one. The machine's load is lopsided: the software renderer keeps about two of its four cores busy through the tour, while the game's main thread needs about 5% of one. A timed frame shares the cores with the renderer's work, which is one way the same build can run at different speeds from one session to the next.

A fair comparison

A tool that times builds in turns

So that the next comparison starts fair, the method is now a tool, tools/perf-compare.mjs. Give it two or more builds. It runs the frame-time tour of each in turns over several rounds, in blocks that form a Latin square: within each block, every build runs once in every place. It then fits each run's average frame on its round, its place and its build, and prints each build's difference from the first with a 95% interval. The arithmetic is in tools/perf-stats.mjs, with no other libraries.

Before trusting it, the statistics were checked on made-up runs with known differences: +0.50 and −0.10 ms for the builds, +0.30 and −0.20 for the places, a drift from round to round, and noise. The fit gave back +0.49 and −0.11 ms for the builds and +0.32 and −0.18 for the places, each inside its interval. The orders were checked to put every build once in every place in each block for two, three and four builds. Given a fixed order, the fit refuses to answer, because it cannot tell the place from the build.

node tools/perf-compare.mjs old/index.html dist/index.html --rounds 6 --size 844x390 --dpr 2
The phone check

The map check drags before it taps

The phone check opens the full map and taps three places in turn, as a player would: Moose Lake, Bear Falls, and the river just below Salmon Bend. The map opens zoomed in, centred on the player at Hotrod Landing. At that zoom Bear Falls lies off the top of the map. In the last round, its dot worked out to 415, -16, 16 points above the top of the screen. The tap went to that point and hit nothing, so Moose Lake stayed selected. The check printed "selected moose" and carried on, because nothing in it could fail. The game was fine, but the test was not testing what it said.

Now the check does what a player does: it drags the map until Bear Falls is in view, then taps it. A new drag step in the test harness moves a finger across the screen in twelve steps. The finger is made of the browser's touch events, so the map gets the same pointer events a real finger makes. The step works out where to drag from where the place sits on the map at that moment, so it keeps working if the map's size or zoom changes. If the drag would start on something other than the map, such as the place card, the step reports that instead of dragging. The river tap gets the same treatment: a second drag brings that point to the middle before the tap.

Limits

What this report cannot show

  • No real iPhone or iPad was used. The map check runs in Chromium set up like an iPhone 15 on its side: 844 by 390, touch, and Safari's user agent. The drag is sent as touch events through Chromium's DevTools protocol, which the browser turns into the pointer events the map listens to. Safari on iPhone also makes pointer events from touches, but the check proves the map follows a drag, not how the drag feels under a finger.
  • Frame times come from a software renderer on the processor, many times slower than a phone's graphics chip, and the draw calls themselves are skipped. They compare builds on one machine; they do not predict a phone's frame rate.
  • The smallest cost these runs could see is about 0.34 ms a frame at 320 by 180 and 0.54 ms at an iPhone's size: the half-widths of the 95% intervals. A real cost smaller than that, such as 0.1 ms, could still be there.
  • The machine's speed changes from session to session. The same tour ran at 13.5 to 14.5 ms a frame in one session and about 10.8 ms in a later one, and the average frame of a round changed by 22% from one round to the next in the four-build experiment. Taking turns and fitting the round takes out a change between rounds, but not one inside a round, which is what made the four-build split too noisy to read. A difference found in one session is therefore worth making again in another before it is believed.
  • Processor time per thread is read every half second. A thread's last half second before it ends can be missed, the same way for both builds, so the totals compare the builds rather than give an exact account. They show work; time a thread spends waiting for a free core shows only in the frame times.
  • The tours play no announcer lines. The warm-up's eleven clips are decoded in every tour, about 1.5 s after the start, but nobody catches a fish on the tour, so a line being played was not timed. Playing a clip is the browser's sound work, away from the thread that draws, and the round before measured that the music dips and comes back as planned.
  • The first three rounds share one order (no warm-up, last round's, this one), drawn at random. They are kept: with the six balanced rounds after them, every build ran first, second and third three times each.
  • Sources were read through web search. curl is blocked for every host in this environment, so the pages below were found and summarised by search, not downloaded in full. To allow hosts: the cloud environment menu in the session's title bar, then Edit, then Network access (a broader level, or Custom with the hosts added under Allowed domains); the steps are at https://code.claude.com/docs/en/cloud-environments#network-access.
What would change this conclusion

What would change this conclusion

The conclusion: the announcer's voice costs no frame time that holds up. Timed in turns over nine rounds at the smallest size, this build is +0.18 ms a frame against last round's (95% interval −0.16 to +0.52). At an iPhone's size, one session of six rounds found it 0.97 ms a frame slower (95% interval +0.72 to +1.22), in every round; the same six rounds made again found −0.02 ms (−0.56 to +0.52), and no thread of the browser does more work with this build. The 0.7 ms from the last round came from the order of the runs, so the game stays as it is. The phone check now really taps Bear Falls, and future comparisons have a tool that times builds in turns. This conclusion would change if:

  • A real phone shows a steady cost. These tests time the processor's side of a frame in a browser that draws in software, and an iPhone's Safari handles decoded sound its own way. The test that would settle it is last round's build and this one taking turns on the same iPhone, timed with Safari's Web Inspector.
  • The 1 ms at an iPhone's size comes back. It was measured in one session, when the tour ran at 13.5 to 14.5 ms a frame, against about 10.8 ms when it was made again. If a later session finds it again, the next test is the four builds in turns with 90 frames at each place and eight rounds, so that the split between the recordings and the full-screen buttons is as precise as the first comparison was; the four-build test here, with 60 frames and four rounds in a noisy session, could not split it.
  • The cost is smaller than these runs can see. The 95% interval reaches about 0.34 ms a frame either side of the estimate at the smallest size and 0.54 ms at an iPhone's size, so a cost of 0.1 or 0.2 ms could still be there; the best estimates for this build are +0.18 and −0.02 ms, and for the build without the warm-up +0.02 ms. The interval narrows with the square root of the number of rounds: four times as many rounds would halve it. If a cost of that size showed up, the warm-up is the first thing to try without, since the first line would then decode when it is first said.
  • You notice a stutter when the announcer speaks. That would be a different cost from the one tested here, because the tours never play a line: nobody catches a fish on them. Decoding and playing a clip are the browser's sound work, away from the thread that draws, but a phone could still show a hitch at that moment, and the place to look would be the first line after the start.
  • A phone runs short of memory. The warm-up keeps eleven decoded clips ready: 9.2 seconds of sound, about 1.6 MB, even when the announcer is switched off or a device voice is picked. Nothing here showed that this matters. If it did, the warm-up could skip players who do not use the game's voice.
  • The map changes so the middle is covered. The drag starts near the middle of the map and checks what is under the finger first. If a later change put a panel over that spot, the check would print that the drag would start on that panel rather than drag, and the tap on Bear Falls would then fail visibly instead of silently.
